# GazeTracker — Phase 1 (Face Mesh Verification)

iOS app that runs MediaPipe Face Mesh on the front camera and overlays
all 478 landmarks live on screen, so you can verify Stage 1 of the
pipeline before building anything else.

## Status: ready to run

Everything is wired. The Xcode project, SPM dependency, model file, and
Info.plist all exist and the app **already compiles cleanly** (verified
with `xcodebuild` against iOS 15+).

```
GazeTrackerPhase1/
├── GazeTrackerPhase1.xcodeproj/    # Generated by xcodegen — open this
├── GazeTrackerPhase1/
│   └── Info.plist                  # Auto-generated, has NSCameraUsageDescription
├── Sources/                        # 6 Swift files (camera, MediaPipe, UI)
├── Models/face_landmarker.task     # 3.6 MB MediaPipe model (already in bundle)

```

## Run on your iPhone (3 steps)

1. **Open the project**
   ```bash
   open GazeTrackerPhase1.xcodeproj
   ```

2. **Set your signing team**
   Click the `GazeTrackerPhase1` target → **Signing & Capabilities** tab →
   pick your Apple ID under "Team". (No team = code-signing fails on device.)

3. **Run**
   Plug in your iPhone, select it as the run destination, press ⌘R.
   The first build takes ~30 s while Xcode resolves the SwiftTasksVision
   package and downloads the MediaPipe XCFramework.

The simulator will *launch* but the camera preview will be black —
simulators have no real camera. You need a physical iPhone to see
landmarks.

## What you should see

Live front-camera feed with bright green dots covering your entire face
(forehead, eyes, nose, lips, jawline). HUD up top:

```
Faces: 1     Landmarks: 478     FPS: ~30
```

If `Faces: 0` while your face is clearly visible:
1. Is there enough light?
2. Black preview = camera permission denied → Settings → GazeTrackerPhase1
   → Camera.
3. Crash on launch about "FaceLandmarker init failed" → confirm
   `face_landmarker.task` is in the bundle (Build Phases → Copy Bundle
   Resources should list it).

## How this was built (for reference)

- **`project.yml`** declares the project. Re-run `xcodegen generate`
  whenever you change it.
- **SPM dependency**: `https://github.com/paescebu/SwiftTasksVision.git @ 0.10.21`
  — community wrapper around the official `MediaPipeTasksVision` CocoaPod.
  Module name is identical, so `import MediaPipeTasksVision` Just Works.
- **Architecture**:
  - `CameraManager` — AVFoundation front-camera capture, portrait + mirrored
  - `FaceLandmarkerService` — MediaPipe `FaceLandmarker` in `.liveStream` mode
  - `GazeViewModel` — glues camera frames → landmarker → @Published landmarks
  - `CameraPreview` — `UIViewRepresentable` hosting `AVCaptureVideoPreviewLayer`
    plus a `CAShapeLayer` overlay drawing the 478 dots with proper
    aspect-fill coordinate mapping
  - `ContentView` / `GazeTrackerApp` — SwiftUI shell

## Study protocol: calibration → validation → experiments

The app runs a fixed protocol. **All on-screen instruction text has been
removed** from calibration and from all four experiments — participants are
briefed verbally, and the screens carry only the stimulus plus minimal
progress/feedback. Every run writes a self-describing bundle to
`Documents/experiment_runs/` (`samples.csv` + `trials.csv` + `meta.json`,
zipped) and appends to a cumulative per-experiment master log.

### 1. Calibration
Nine dots, one at a time, 1 s settle + 2 s capture each. Closed-form
least-squares fit of the screen pose (`ScreenMapper`) plus a per-target local
correction (`CalibrationModel`).

### 2. Calibration validation *(new)*
Runs **automatically as soon as calibration completes**. All 9 dots are shown
**simultaneously** and the participant looks at them **in any order**. A dot is
scored once the gaze holds it continuously for 1 s; only samples from inside
that satisfied dwell window are used, so the saccade into a dot never pollutes
its error.

The screen then reports a **verdict** — good / marginal / poor / incomplete —
based on mean error in degrees, so a bad fit is caught here rather than
silently corrupting an experiment. From the verdict screen you can Accept,
Re-validate, or Re-calibrate. This is the step that replaced *assuming*
calibration worked.

### Experiment 1 — Grid accuracy vs. grid resolution
Sequential highlighted cells across the selectable grid resolutions —
**3×3 (×2), 4×4, 5×4, 6×4, 6×9, 9×9 and 9×9 walking** (3×3 repeats twice so
its trial count is comparable to the others). Reports per-cell
accuracy (hits / attempts), overall accuracy, and mean error in **both px and
degrees**, alongside the cell's angular tolerance (half a cell) — mean error
above that tolerance means the grid is finer than the tracker can resolve.

### Experiment 2 — Fixation stability
A **4×4 grid** of boxes. One cell at a time holds a single red circle at its
centre; the participant fixates it (1 s unscored settle, then 4 s scored),
then the circle moves to the next cell in shuffled order until all 16 have
been held — roughly 80 s per run, ~120 frames per cell at 30 Hz.

Reports, **per cell and aggregated**: mean deviation from the circle centre,
radial SD, **RMS scatter (precision)**, bias, per-axis SD, and containment —
plus the worst single cell. Aggregates average the per-cell statistics rather
than pooling all samples, since pooling would mostly measure the grid geometry
rather than tracker noise.

Sweeping 16 positions rather than one shows whether the noise floor is uniform
or degrades toward the corners, which the results screen draws as a per-cell
precision map. No live gaze cursor is drawn here on purpose — a moving cursor
becomes a moving stimulus and the participant tracks it instead of the circle.

This measurement bounds the others: no grid experiment can resolve better than
the noise floor this reports.

### Experiment 3 — Image-based communication task
A 4×3 grid of word images. The participant composes **"I want to drink water"**
by fixating each word in order (1 s dwell to select), among 7 distractors
(*eat, sleep, help, more, please, stop, home*). **Each selection is spoken
aloud** via `AVSpeechSynthesizer`.

Every selection is appended to the composed sentence, right or wrong — that is
what a real AAC device does, and suppressing wrong picks would hide the error
rate the experiment exists to measure. Reports correct/incorrect selections,
selection accuracy, seconds per word, and an effective **words-per-minute**
rate. Word positions are shuffled per run so position learning can't inflate
the rate.

The word tiles live in `Resources/Experiment3Images/` and are generated by:

```bash
python3 Tools/gen_word_images.py     # needs Pillow
```

Replace those PNGs with real pictograms using the same `word_<lowercase>.png`
names to swap the vocabulary's artwork; the overlay falls back to rendering
the word as text if an image is missing.

### Experiment 4 — Prompted predictive communication *(new)*
A **3×3 grid** whose contents are rebuilt after every selection by a next-word
predictor. The app **asks a question** ("How are you feeling today?"), and the
participant answers by dwelling their way down the prediction tree.

Nine cells: **7 prediction slots** plus `⌫ back` (bottom-left) and `✓ done`
(bottom-right) at fixed positions all run, so the controls become a motor habit
rather than a search. The controls dwell **1.5 s** against 1.0 s for words —
they sit in the corners, where Experiment 2 reports the worst scatter, and an
accidental `⌫` destroys a word.

Each trial is two phases. The question is **spoken and shown while the grid is
hidden**; then the text disappears, the grid goes live and the response clock
starts. That is how the no-instructions rule is honoured here — nothing
competes with the stimulus while gaze is scored, and listening time never
enters the rate. Every grid change raises a **0.4 s lockout** in which samples
are logged but no dwell accrues, so the fixation already in flight cannot be
charged to a word the participant has not yet seen.

Cells are as wide as Experiment 3's and a third taller, so this asks *less* of
the estimator than Experiment 3 does. The point is what that buys: seven slots
reach ~7⁴ ≈ 2 400 four-word sentences where a static 9-cell grid reaches almost
none. Prediction is what makes a grid coarse enough for the tracker to resolve
still expressive enough to talk with.

**Two conditions**, both from the idle screen and both tagged in the log:

  - **Cued** — the participant is told which answer to give. `isCorrect` is
    defined exactly as in Experiment 3, so accuracy and words-per-minute are
    directly comparable to it. One of the five questions is cued with
    **"I want to drink water"** — Experiment 3's exact sentence, giving a
    like-for-like static-vs-predictive comparison at identical dwell time.
  - **Free** — the participant answers as they like. No correctness; scored on
    time-to-answer, `⌫` corrections and selection overhead.

Reports selection accuracy, seconds per word, words-per-minute, corrections and
**selection overhead** (dwells spent ÷ dwells the answer needed) — plus the
metric the design exists for, **predictor hit rate**: how often the needed word
was on the grid *at all*. That splits *the tracker picked the wrong cell* from
*the right word was never offered*, which Experiment 3 cannot distinguish.

The question set and its response trees live in `Sources/ResponsePredictor.swift`.
The shipped predictor is a hand-authored trie, not a language model, and
deliberately so: it is deterministic (every participant sees the same grid at
the same step), adds no inference latency to the rate metric, and can be
*checked* before the run that every cued answer is reachable — a run refuses to
start otherwise. `ResponsePredictor` is a protocol, so an n-gram table or an
on-device LM can be added later as a second conformance and a condition flag.

### A note on degrees
Angular error uses the calibration's fitted `|tz|` as the eye-to-screen
distance (`VisualAngle`). That distance is **virtual** — self-consistent with
the calibration that produced the prediction, but not a physically measured
viewing distance — so degrees are comparable across conditions within a
session, not across participants with very different fits.
